# Workflow интеграционного контура (Cursor Component Factory)

Регламент обновления опубликованных версий компонентов и проверки их взаимодействия.
Обязательное ядро правил: [CORE_WORKFLOW.md](CORE_WORKFLOW.md).

Интеграционный контур **не является местом для разработки бизнес-логики компонентов**. Здесь фиксируются версии зависимостей, сквозные сценарии взаимодействия, интеграционные автотесты и доказательства совместимости.

---

## 1. Граница рабочей области (Scope Boundary)

Workflow применим как к микросервисной архитектуре, так и к системам 1С:

- **Полирепозиторий (Polyrepo):** Откройте корень интеграционного Git-репозитория. Репозитории компонентов подключаются только для чтения (read-only) или как опубликованные зависимости.
- **1С:Предприятие:** Интеграционная база данных, в которую загружается целевая конфигурация и подключаются скомпилированные файлы расширений (`.cfe`).

### Структура интеграционного контура
```text
/
├── README.md                 # Описание системы, статус Integrated, инструкции запуска контура и тестов
├── product/
│   └── features/          # Сквозные пользовательские сценарии
├── contracts/             # Машиночитаемые схемы контрактов (OpenAPI, AsyncAPI, Proto)
├── dependencies/
│   └── manifest.<format>  # package.json, requirements.txt, go.mod, version-lock.json
├── scenarios/             # Спецификации сквозных сценариев
├── integrations/
│   └── status.<format>    # Реестр подтвержденных статусов Integrated
└── tests/
    └── integration/       # Сквозные и контрактные тесты связей
```

Формат манифеста зависимостей и реестра статусов определяется используемым технологическим стеком.

---

## 2. Формат интеграционной записи

Статус `Integrated` относится исключительно к конкретной паре версий и контракту. Запись в реестре (`integrations/status.*`) содержит:

```yaml
consumer: "order-service v2.1.0"
provider: "billing-service v1.3.0"
contract: "contracts/api/discount-v1.yaml (v1.3.0)"
scenario: "scenarios/apply-discount.md"
checks:
  success: "Test calculateDiscount_Success passed (200 OK)"
  expectedFailure: "Test calculateDiscount_InvalidPromo passed (404 Not Found)"
status: "Integrated"
approvedByHuman: "Илья (Аналитик) 2026-08-16"
```

ИИ категорически **запрещено** устанавливать статус `Integrated` без прямого подтверждения человеком.

## 3. Сквозная итерация интеграции (Шаг за шагом)

> **Правило безопасности:** В одной задаче обновляется ровно **одна зависимость** и проверяется **одна связь**.

### Шаг 1. Выбор связи и постановка задачи
Аналитик указывает пару взаимодействующих компонентов и целевую версию поставщика (например: `order-service` → `billing-service` до версии `v1.3.0`).

### Шаг 2. Проверка готовности артефактов
- Обе версии компонентов должны иметь статус `Ready` и проверенную ревизию (Git Tag или опубликованный пакет).
- Машиночитаемый контракт нужной версии доступен в `contracts/`.

### Шаг 3. Обновление одной зависимости
ИИ изменяет версию поставщика в манифесте зависимостей (`package.json`, `requirements.txt`, `manifest.json` и т.п.).
Исходный код компонентов при этом **не редактируется**.

### Шаг 4. Проверка связи (Интеграционные тесты)
ИИ запускает сквозные проверки взаимодействия:
1. **Успешный обмен (Happy Path):** данные потребителя соответствуют контракту → поставщик возвращает корректный ответ → потребитель успешно его обрабатывает.
2. **Ожидаемый отказ (Expected Failure):** потребитель передает невалидные данные → поставщик возвращает ожидаемый код ошибки (например, 400 или 404) → потребитель безопасно обрабатывает ошибку.
3. **Регрессионные тесты:** проверка, что остальные связи интеграционного контура не сломались.

### Шаг 5. Разбор несовместимостей (при ошибках)
Если интеграционный тест упал:
- ИИ **запрещено** «на лету» патчить код компонентов или ослаблять схемы.
- ИИ останавливается и формирует отчет:
  * Ожидаемое поведение (по контракту);
  * Фактическое поведение (что вернул сервис);
  * Затронутые потребители;
  * Репозиторий-владелец, в котором нужно исправить дефект и выпустить новую версию `Ready`.

### Шаг 6. Подтверждение статуса `Integrated`
Аналитик проверяет отчет тестов и дает разрешение:
```text
Разрешаю записать Integrated для связи order-service v2.1.0 -> billing-service v1.3.0 по контракту discount-v1.yaml v1.3.0.
```

После этого:
1. ИИ делает запись в реестре `integrations/status.*`.
2. ИИ актуализирует `README.md` (статус связей, версии зависимостей, инструкции запуска окружения и E2E тестов).
3. Формирует интеграционный коммит.

## 4. Специфика интеграции в 1С:Предприятие

Для проектов на платформе 1С интеграционный процесс выглядит следующим образом:

1. **Подключение расширения:**
   * Скомпилированный файл расширения (`.cfe`) версии `Ready` загружается в тестовую информационную базу через командную строку (`1cv8` / `vrunner`).
2. **Проверка метаданных:**
   * Проверяется отсутствие конфликтов расширения с основной конфигурацией (контролируемые свойства, заимствованные объекты).
3. **Запуск BDD-сценариев Vanessa-Automation:**
   * Прогоняются интеграционные сценарии `tests/integration/*.feature`, проверяющие сквозные цепочки документов и вызовы сервисов.
4. **Фиксация статуса:**
   * После прохождения сценариев фиксируется статус `Integrated` расширения в целевой конфигурации.

---

## 5. Чек-лист готовности `Integrated`

Связь считается интегрированной только при выполнении всех условий:

- [ ] В манифесте обновлена ровно одна версия зависимости.
- [ ] Обе версии компонентов имели подтвержденный статус `Ready`.
- [ ] Версия и схема контракта зафиксированы в `contracts/`.
- [ ] Успешный сценарий обмена данными прошел проверку.
- [ ] Сценарий ожидаемого отказа (ошибочный путь) прошел проверку.
- [ ] Затронутые регрессионные тесты интеграционного контура не упали.
- [ ] Исходный код компонентов не изменялся в рамках этой задачи.
- [ ] В `README.md` зафиксированы статус Integrated, актуальные версии компонентов и инструкции по запуску контура и сквозных тестов.
- [ ] Человек явно разрешил присвоение статуса `Integrated`.
- [ ] Запись о связке добавлена в интеграционный реестр.
