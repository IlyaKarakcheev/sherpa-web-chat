# Практическое руководство пользователя (Cursor Component Factory)

Пошаговое руководство для аналитиков, инженеров и архитекторов по быстрому фабричному созданию и интеграции компонентов с помощью ИИ в Cursor.

Общие правила: [CORE_WORKFLOW.md](CORE_WORKFLOW.md)  
Режимы: [COMPONENT_REPO_WORKFLOW.md](COMPONENT_REPO_WORKFLOW.md) (разработка) и [INTEGRATION_REPO_WORKFLOW.md](INTEGRATION_REPO_WORKFLOW.md) (интеграция).

---

## 1. Концепция: как строится работа

Вся работа с ИИ строится на **минимальном количестве действий человека**:

1. **Человек ставит бизнес-задачу.**
2. **ИИ переводит её в структурированный документ и контракт, задавая вопросы при неясности.**
3. **Человек согласует документ.**
4. **ИИ реализует логику, сам поднимает авто-моки, пишет и прогоняет тесты.**
5. **Человек проверяет отчет и утверждает статус.**

## 2. Создание репозиториев (Полирепозитории / Вариант Б)

### Шаг 1. Создание репозитория компонента (`/new-component`, `/new-repo`)
Для каждого микросервиса, модуля или расширения создается отдельный автономный Git-репозиторий:
```text
/new-component billing-service Путь: d:\__ai-factory\projects\billing-service Назначение: расчет персональных скидок и промокодов. Стек: REST OpenAPI
```
*Что сделает ИИ:*
- Создаст двухуровневую контрактную структуру `product/features/`, `contracts/protocol/`, `contracts/domain/`, `contracts/front/`, `src/`, `mocks/`, `tests/`.
- Создаст паспорт `COMPONENT.md` (статус `Prototype`), стартовый `README.md` с инструкциями и черновики контрактов с парным мок-пакетом.
- Скопирует правила `.cursor/` и документацию `fast-workflow/`.
- Инициализирует собственный независимый Git-репозиторий (`git init -b main`) и сделает первый коммит.

### Шаг 2. Создание интеграционного репозитория (`/new-integration`)
Для интеграционного контура (системная сборка, API Gateway, реестр интеграций) создается отдельный репозиторий:
```text
/new-integration ecommerce-platform Путь: d:\__ai-factory\projects\ecommerce-platform Назначение: Интеграционный контур и API Gateway платформы
```
*Что сделает ИИ:*
- Создаст структуру интеграционного контура: `contracts/api/`, `dependencies/`, `integrations/status.yaml`, `scenarios/`, `tests/integration/`, стартовый `README.md`.
- Скопирует правила `.cursor/` и документацию `fast-workflow/`.
- Инициализирует собственный независимый Git-репозиторий (`git init -b main`) и сделает первый коммит.

### Работа в Cursor (Multi-Root Workspace)
- **Изолированная разработка:** Открывайте папку одного компонента в Cursor (`File -> Open Folder...`).
- **Сквозная интеграция и отладка нескольких репозиториев:** Добавьте несколько репозиториев в одно окно через `File -> Add Folder to Workspace...`. Каждый репозиторий сохраняет собственный независимый `.git` и историю коммитов.

## 3. Разработка компонента (`Prototype → Ready`)

### Вариант А. Через быстрые команды (Cursor Skills)

#### 1. Постановка задачи и контракт
Напишите в чате:
```text
/spec Создать компонент расчета скидок billing-service. Метод: расчет скидки по промокоду. Вход: промокод и сумма корзины, выход: размер скидки и итоговая сумма.
```
*Что сделает ИИ:*
- Создаст или обновит `COMPONENT.md`.
- Создаст спецификацию `product/features/discount.md`.
- Создаст схему контракта `contracts/api/discount-v1.yaml` (OpenAPI 3.1).
- Если есть неясности (например, максимальный % скидки) — задаст 1–2 конкретных вопроса.

#### 2. Согласование
Проверьте контракт и напишите:
```text
Максимальная скидка 50%. Спецификацию и контракт утверждаю.
```

#### 3. Реализация и авто-проверка
Запустите реализацию:
```text
/implement
```
*Что сделает ИИ под капотом:*
- Автоматически подключит мок-сервер или фикстуры по контракту (Zero-Manual Mocks).
- Напишет исходный код в `src/`.
- Напишет и прогонит тесты в `tests/` (успешный сценарий + некорректный промокод + превышение скидки).
- Предоставит отчет с результатами тестов.

#### 4. Приемка и релиз
Если результат проверен и принят:
```text
Разрешаю статус Ready для версии 1.0.0. Сделай коммит и тег billing-service-v1.0.0.
```
*Что сделает ИИ:*
- Зафиксирует статус `Ready` в `COMPONENT.md`.
- Актуализирует `README.md` (версия, статус, чейнджлог, команды запуска и тестов).
- Создаст коммит и релизный Git Tag.

### Вариант Б. Через обычный текстовый диалог

Если вы предпочитаете общаться обычными сообщениями:

#### Сообщение 1 (Постановка):
```text
Работаем по @fast-workflow/COMPONENT_REPO_WORKFLOW.md и @.cursor/rules/component-repo-workflow.mdc.

Я хочу создать компонент <название>.
Его назначение: <описание бизнес-смысла>.
Подготовь COMPONENT.md, спецификацию фичи и схему контракта. Код пока не пиши.
Если есть неоднозначности — задай вопросы.
```

#### Сообщение 2 (Согласование и старт реализации):
```text
Ответы на вопросы: <ответы>.
Контракт и спецификацию утверждаю.
Разрешено менять только: src/, mocks/, tests/.
Реализуй компонент с авто-моками, напиши тесты (успех + отказ) и покажи результаты проверок.
```

#### Сообщение 3 (Приемка):
```text
Результаты проверок приняты. Разрешаю статус Ready для версии <версия>.
Создай коммит с сообщением "Prepare <компонент> v<версия>" и поставь Git Tag <компонент>-v<версия>.
```

## 4. Обработка замечаний (Что делать, если что-то пошло не так)

### Сценарий 1. Нашли баг или ошибку в коде (Требования не менялись)
*Пример:* Тест упал, неверный формат даты, неправильный код ошибки HTTP 500 вместо 400.
```text
Ошибка: при пустом промокоде возвращается 500 вместо 400 Bad Request.
Исправь, добавь тест на этот кейс и покажи обновленный отчет.
```
*ИИ сразу переходит к правке кода и тестов (Шаг 4), не меняя спецификации.*

### Сценарий 2. Изменились требования или нужна новая функция (Scope Change)
*Пример:* Захотели добавить поле `bonus_points` или изменить расчет.
```text
Нужно добавить в контракт опциональное поле partner_id и расчет бонусов.
Обнови спецификацию и контракт по правилам SemVer (Minor). Код пока не меняй.
```
*ИИ обновляет схему контракта (v1.1.0), человек согласует ее, и только после этого обновляется код.*

### Сценарий 3. Ломающее изменение (Major Breaking Change)
*Пример:* Переименование обязательного поля `promo_code` в `coupon_id`.
```text
Требуется переименовать promo_code в coupon_id.
Оформи контракт v2.0.0 (Major) в contracts/api/discount-v2.yaml.
```

## 5. Интеграция компонентов (`Integrated`)

Когда поставщик данных получил статус `Ready`, переходим в интеграционный репозиторий / приложение.

### Быстрая команда
```text
/integrate order-service billing-service v1.2.0
```

### Или обычное сообщение:
```text
Работаем по @fast-workflow/INTEGRATION_REPO_WORKFLOW.md и @.cursor/rules/integration-repo-workflow.mdc.

Текущий этап: обновление одной зависимости.
Связь: order-service -> billing-service.
Обнови billing-service до версии v1.2.0.
Контракт: @contracts/api/discount-v1.yaml (v1.2.0).

Разрешено менять только: манифест зависимостей и tests/integration/discount/.
Исходный код компонентов не изменяй.
Проверь успешный обмен и один ожидаемый отказ.
```

### Подтверждение интеграции:
После того как тесты взаимодействия прошли успешно:
```text
Разрешаю записать статус Integrated для order-service -> billing-service v1.2.0 по контракту discount-v1.yaml.
```

## 6. Специфика для разных платформ и стеков

### REST API / Микросервисы (Node.js, Go, Python, Java)
- Схема контракта: `contracts/api/<service>.yaml` в формате **OpenAPI 3.1**.
- ИИ автоматически поднимает мок-сервер через `npx @stoplight/prism-cli mock contracts/api/...` или `MSW`.

### Модули TypeScript / Frontend
- Схема контракта: `contracts/domain/<models>.ts` на базе **Zod** или **TypeBox**.
- Автогенерация моков: через фабрики данных с `@faker-js/faker`.

### 1С:Предприятие (Конфигурации и расширения .cfe)
- Хранение в Git: проект 1C:EDT или текстовая выгрузка XML/BSL.
- Юнит-тесты и моки: модули **`YAxUnit`** (`tests/unit/`).
- BDD сценарии: файлы Gherkin `.feature` в `tests/scenarios/` с прогоном через **`Vanessa-Automation`**.
- Сборка артефакта: через CI (`vrunner build-cfe`) с прикреплением `.cfe` к релизу.

## 7. Памятка: когда остановить ИИ

Немедленно остановите выполнение задачи, если ИИ:
1. Пытается редактировать код соседнего сервиса или чужого пакета в рамках одной задачи.
2. Самовольно изменил утвержденный контракт без предварительного согласования схемы.
3. Удалил или ослабил тесты, чтобы получить успешный статус.
4. Сам себе присвоил статус `Ready` или `Integrated` без вашего явного одобрения.
5. Предложил ручное написание громоздких моков вместо автогенерации по контракту.
