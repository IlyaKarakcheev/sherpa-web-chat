# Workflow репозитория / модуля компонента (Cursor Component Factory)

Регламент автономной разработки одного программного компонента или модуля.
Обязательное ядро правил: [CORE_WORKFLOW.md](CORE_WORKFLOW.md).

Цель режима — подготовить воспроизводимую, изолированно протестированную версию компонента со статусом `Ready`. Интеграция версий выполняется отдельно по [INTEGRATION_REPO_WORKFLOW.md](INTEGRATION_REPO_WORKFLOW.md).

---

## 1. Граница рабочей области (Scope Boundary)

Workflow регламентирует разработку в изолированном репозитории компонента:

- **Полирепозиторий (Polyrepo):** Откройте в Cursor корень Git-репозитория компонента. Внешние репозитории не изменяются.

### Структура компонента
```text
/
├── README.md               # Описание проекта, статус, чейнджлог, запуск и тесты
├── COMPONENT.md           # Карточка и паспорт компонента
├── product/
│   └── features/          # Спецификации пользовательских требований
├── contracts/
│   ├── api/               # OpenAPI 3.1 схемы (HTTP/REST)
│   ├── events/            # AsyncAPI / JSON Schema (очереди и шина)
│   └── domain/            # Zod / Pydantic / Proto / XSD схемы
├── src/                   # Исходный код компонента
├── mocks/                 # Автоматически сгенерированные заглушки и мок-серверы
└── tests/                 # Модульные, интеграционные и сценарные тесты
```

Каталоги создаются по мере появления соответствующих артефактов.

---

## 2. Принцип Zero-Manual Mocks (Полная автогенерация заглушек)

Разработчик и аналитик **не тратят время на ручное написание моков**. Заглушки генерируются автоматически напрямую из схем контрактов:

1. **HTTP / REST (OpenAPI 3.1):**
   * Автоматический запуск мок-сервера через `Prism`, `MSW` (Mock Service Worker) или `WireMock`.
   * Мок-сервер из коробки поддерживает возврат `200 OK` со сгенерированными валидными данными, `400 Bad Request` при некорректных параметрах и `500 Internal Error`.
2. **TypeScript / JavaScript (Zod / TypeBox):**
   * Автогенерация фабрик тестовых данных через связку `@faker-js/faker` + Zod-схема.
3. **Python (Pydantic v2):**
   * Генерация тестовых фикстур через `polyfactory` / `pydantic-factories`.
4. **1С:Предприятие (BSL / YAxUnit):**
   * Автогенерация мок-объектов и шпионов для `YAxUnit` по сигнатурам экспортных методов общих модулей и XDTO/JSON-структурам.
5. **Очереди и события (AsyncAPI / JSON Schema):**
   * Генерация синтетических сообщений для брокеров по схемам событий.

## 3. Сквозной цикл разработки `Prototype → Ready`

Разработка компонента выполняется по 5 шагам:

### Шаг 1. Постановка задачи
Аналитик или инженер формулирует требование простыми словами (бизнес-смысл, пользовательский сценарий).

### Шаг 2. Документирование и контракт
ИИ подготавливает или обновляет:
1. Документ требования: `product/features/<feature-name>.md`.
2. Карточку компонента: `COMPONENT.md` (назначение, входы, выходы, границы).
3. Машиночитаемую схему контракта в `contracts/`.
4. Список открытых вопросов (если есть неоднозначность).

### Шаг 3. Согласование человеком
Человек проверяет спецификацию, закрывает открытые вопросы и дает согласие:
```text
Спецификацию и контракт утверждаю. Реализуй.
```

### Шаг 4. Изолированная реализация и самопроверка (ИИ)
ИИ работает строго в границах разрешенного пути:
- Реализует логику в `src/`.
- Подключает сгенерированные моки из схемы контракта.
- Пишет и запускает обязательный набор проверок:
  * **Успешный сценарий (Happy Path);**
  * **Некорректный вход (Validation Error / 400);**
  * **Отказ зависимости (Dependency Failure / 500 / Timeout);**
  * **Пустой результат (Empty List / 404);**
  * **Повторный вызов (Idempotency), если применимо.**
- Формирует технический отчет с доказательствами тестов.

### Шаг 5. Приемка и подтверждение статуса `Ready`
Аналитик проверяет отчет.
- При наличии багов — указывает на ошибку (ИИ возвращается на Шаг 4).
- При изменении требований — обновляется контракт с учетом SemVer (ИИ возвращается на Шаг 2).
- При успешной приемке — аналитик дает разрешение:
```text
Разрешаю присвоить версии <version> статус Ready.
```

После этого:
1. В `COMPONENT.md` фиксируется статус `Ready` и проверенная ревизия.
2. В `README.md` обновляются статус, версия, краткое описание изменений (чейнджлог) и актуальные инструкции по запуску и тестированию.
3. Создается коммит и Git Tag.

## 4. Специфика компонентов 1С:Предприятие (Конфигурации и расширения .cfe)

Для разработки компонентов на платформе 1С:Предприятие действуют следующие стандарты:

1. **Хранение в репозитории:**
   * Исходный код хранится в текстовом представлении (проект 1C:EDT или XML/BSL выгрузка конфигуратора). Бинарные `.cf`/`.cfe` в Git не коммитятся.
2. **Паспорт компонента (`COMPONENT.md`):**
   * Обязательно указываются: версия платформы 1С, режим совместимости, целевая конфигурация (например, `1С:ERP 2.5.12+`), признак безопасного режима.
3. **Модульное тестирование:**
   * Тесты пишутся на языке 1С с использованием фреймворка **`YAxUnit`** в каталоге `tests/unit/`.
   * Для изоляции вызываемых процедур используются моки и шпионы `YAxUnit`.
4. **Сценарное BDD-тестирование:**
   * Поведение описывается на языке Gherkin в файлах `tests/scenarios/*.feature`.
   * Запуск сценариев выполняется через **`Vanessa-Automation`**.
5. **Сборка артефакта Ready:**
   * CI-скрипты (`vrunner` / `oscript` / `1cv8`) собирают скомпилированный бинарный файл расширения (`.cfe`) или конфигурации (`.cf`), который привязывается к релизному Git Tag.

## 5. Чек-лист готовности `Ready`

Компонент получает статус `Ready` только при выполнении всех пунктов:

- [ ] Назначение, границы и бизнес-правила утверждены аналитиком.
- [ ] Все открытые вопросы закрыты (нет скрытых допущений).
- [ ] Машиночитаемый контракт утвержден и версионирован по правилам SemVer.
- [ ] Автоматические заглушки соответствуют утвержденному контракту.
- [ ] Успешный сценарий и сценарии обработки ошибок проходят локально.
- [ ] В `COMPONENT.md` зафиксированы версия и проверенная ревизия (Git Tag или версия манифеста).
- [ ] В `README.md` зафиксированы статус, версия, чейнджлог и инструкции запуска во всех режимах.
- [ ] Рабочее дерево чистое, коммит сформирован.
- [ ] Человек явно разрешил присвоение статуса `Ready`.
